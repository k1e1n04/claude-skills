# 拡張機能の UX 設計

拡張機能(拡張ポイント、プラグイン、フック、サーバーレス関数など)は、問題解決に実行可能なアプローチが複数あり、どれを選ぶかを利用者に委ねたいときに使う。

## 使いどころの例

- 日付を文字列で受け取るとき、受理するフォーマットを拡張で追加できるようにする
- 多数のデータソースから取り込むとき、データソースの追加を拡張にする
- 機械学習ワークフローの活性化関数など、アルゴリズムの振る舞いを差し替えられるようにする
- 拡張ポイントは単一ノードに限らない。サービスやサーバーレス関数も拡張ポイントになる(例: クラウドプラットフォームがサーバーレス関数で機能を拡張する)

## 設計ルール

- **待つ**: ユースケースを深く理解するまで追加しない。必要になってからリファクタリングで足せる。
- **1 つのことをうまくやる**: 優れた API と同じ。
- **入力と出力を定義して、できることを制御する**。その入出力は、API や設定と同様にユーザーが理解できるものにする。
- **内部構造を露出しない**: 内部データ構造が変わると拡張が壊れる。
- **変更の難しさを織り込む**: 拡張は書かれると変えにくい。利用者が旧バージョンに留まり、長期のメンテナンスコストが増える。可能なら、拡張の内容を本体のコードベースに還元するようユーザーを促す。
- **投資判断**: 拡張を書く人は通常限られる。ただしエコシステムが育てば価値が大きい(例: iOS アプリがスマートフォンを拡張し、多数の開発者を動員した)。その見込みがあるなら投資は正当化しやすい。

## レビュー観点

- [ ] 本当に拡張点が要るか。ユースケースの理解は十分か(早すぎないか)
- [ ] 責務は 1 つか
- [ ] 入出力は明確で、ユーザーが理解できる型か
- [ ] 内部データ構造・内部 API が漏れていないか
- [ ] 本体バージョンアップ時の互換性方針(バージョニング、廃止手順)はあるか
- [ ] 拡張を本体へ還元する導線があるか
