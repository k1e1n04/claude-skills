# 設定の UX 設計

設定ファイル、環境変数、CLI フラグ、設定 UI に適用する。まず「ユーザージャーニーから導く」「イテレーティブにスライスする」を前提にする。

## 設定を導入するか決める

開発者は 2 案で迷うと設定にして判断を押し付けがち。ユーザーはシステムの挙動を開発者より知らないので、たいてい適切に決められない。次の順で検討する。

1. **設定の余地をなくす**: どんな状況でも通用する選択肢を探す
2. **自動で選ぶ**: 実行時に測定・検出して調整する
3. **設定を導入し、妥当な既定値を与える**

判定の問い: **ユーザーは、我々より良い文脈を持っているか?**
- Yes → 設定にする
- No → 設定にしない

### 例

| 項目 | 判定 | 理由 |
|---|---|---|
| サーバーのスレッド数 | 設定にしない。自動測定・調整 | 挙動を最も知るのは設計者。負荷は計測できる |
| モバイルデータ節約(安い時間帯にDLを自動スケジュール) | ユーザーに聞く | ユーザー自身の意図・事情に関する項目で、本人が答えられる |

## 設定を作るときのルール

- **全項目に理にかなった既定値**を持たせる。理解できなければそのままで動くこと。
- 初期質問は簡単なものなら可(例: 所在地)。それでも既定値を用意する(例: 最も人口の多い都市)。
- **答えやすい形で聞く**: 頭の中で換算させない。「最大キャッシュエントリ数」より「キャッシュメモリ上限」。さらに、個別チューニングよりモード選択(サーバー/クライアント等)から詳細を導出する。
- **設定は他の接点と違い、文書化の余地がある**。各項目に、サンプル値・取りうる範囲・意味を、設定ファイルのコメントか設定 UI のツールチップで記載する。
- **未知の設定キーや適用失敗はエラーにする**。黙殺するとデバッグで大量の時間を失う。
- **有効な設定を確認できる**ようにする(例: 起動ログにアクティブな設定、スレッド数、キャッシュ設定などを出す)。
- 入力しやすい UI コントロール(日付・地図・写真など)を使う。

## 良い設定ファイル例(文書化込み)

```yaml
# config.yml
server:
  host: 127.0.0.1   # 待受アドレス。外部公開するなら 0.0.0.0
  port: 8080        # 1024-65535。既定 8080
  timeout:          # 単位: 秒
    server: 30      # 既定 30
    read: 15        # リクエスト読み取り上限。既定 15
    write: 10       # レスポンス書き込み上限。既定 10
    idle: 5         # keep-alive の待機上限。既定 5
```

レビュー時は、この 4 項目(timeout 4 種)も「本当に全部ユーザーが決めるべきか。1 つの `timeout` に畳めないか」と問う。

## レビュー観点

- [ ] その設定は「迷った末の押し付け」ではないか
- [ ] 自動決定・削除できないか
- [ ] 既定値があり、未設定でも動くか
- [ ] 単位・範囲・意味・例が書かれているか
- [ ] ユーザーの言葉で、換算不要に聞いているか
- [ ] 未知キー/不正値でエラーになるか
- [ ] 有効設定を確認できるか
