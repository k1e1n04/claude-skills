# UX レビューの出力形式とチェックリスト

## 出力テンプレート

```
## UX レビュー: <対象>

対象接点: API / 設定 / 拡張機能
想定ユーザー: <誰が、何のために、技術レベル>

### 指摘(重要度順)
1. [原則N] <問題> — <なぜ問題か(ユーザー視点)> → <改善案>
2. ...

### 良い点
- ...

### 未決事項(ユーザー確認が必要)
- <仮説> → <確認したいこと>
```

重要度は、ユーザーが一度使い始めたあとに直しにくいもの(公開 API、拡張の入出力、設定キーの名前と意味)を上位にする。

## 原則別クイックチェック

1. **ユーザー理解**: 利用者像とワークフローが書けるか。観察・計測の手段はあるか
2. **最小限**: 削れる機能・設定・エンドポイントはないか。使える標準はないか
3. **マニュアル不要**: ドキュメントを読まずに最初の成功ができるか
4. **情報交換**: 聞かずに済む情報を聞いていないか。同じことを二度聞いていないか。答えやすい形か
5. **シンプルをシンプルに**: 初回体験の障壁(設定、ボイラープレート、前提知識)は何か
6. **UX 先行**: 実装済みの都合が UX を歪めていないか。公開前にフィードバックを得たか

## 体制のチェック(チーム/プロジェクトのレビュー時)

- [ ] UX の専門知識を持つ人がいる
- [ ] 早い段階から参加している
- [ ] UI 以外(API・設定・拡張機能)も担当範囲に入っている
- [ ] 全体の UX 議論に関与し、提案が反映されている(UI の微調整だけを頼んでいない)
