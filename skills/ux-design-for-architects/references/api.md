# API の UX 設計

プログラム(コード)が使う接点。実際の利用者は、コードを書く開発者。その開発者に最適化する。

## 内部 API と公開 API

- **内部 API**: サービス同士を結ぶ。ほとんどのシステムに存在する。モバイルアプリのバックエンドも将来 API になりうる。
- **公開 API**: 多くは高度なユースケースで、最初の MVP の後に有効化する。競争優位になるデータが漏れる恐れがあり、公開前に評価が必要。
- API の**設計は早期に始める**が、**公開は必要になってから**。公開して他システムが依存すると変更が難しい。可能なら公開前に自分たちが内部で使い、問題を見つけて直す。

## 原則の API への適用

| 原則 | API での意味 |
|---|---|
| 1 ユーザー理解 | 利用する開発者・そのメンタルモデル・ワークフローを知る。例: 書店 API は実店舗の流れ(検索 → 選ぶ → 購入)に沿わせる |
| 2 最小限 | 1 つのことをうまくやる。要るか確信が持てない機能は入れない |
| 3 マニュアル不要 | 学びやすく、誤用しにくく、次のステップが常に明確 |
| 4 情報交換 | 要求する情報を最小に。前の呼び出しの結果をそのまま次に渡せる |
| 5 シンプルをシンプルに | 定型コードを書かせない。初期化だけで最初の操作ができる |
| 6 UX 先行 | 実装前に「使うコード」を先に書いて確かめる |

## 具体策

- **最初の一歩を最短に**: 設定済みクライアントや設定ファイルをダウンロードさせ、設定作業を省く。動くサンプルを添える。
  ```java
  Bookshop bookShop = new Bookshop("/path/to/downloaded/config/file");
  Book[] books = bookShop.search("Design Deeply");
  bookShop.buy(books[5]);
  ```
- **不透明なオブジェクトで状態を引き回す**: 後続呼び出しで情報が必要なら、それを含んだオブジェクトを返し、クライアントはそれを渡すだけにする。`search` が返した `Book` をそのまま `buy` に渡せ、内部フォーマットを知らせない。
- **標準を採用する**: OAuth, OpenID など。標準に改善の余地があっても、採用し、必要なら標準の上にラッパーを被せて UX を補う。技術的な最善より、勢いのある標準に賭ける。
- **トランスポートはユースケースで選ぶ**: 多くは HTTP。メッセージキュー等もありうる。
- **クライアントライブラリを提供する**: クライアントとサーバーの両方を制御できると変更の余地が増え設計が単純になる。ただし多様な環境に対応する手間はかかる。
- **最初からバージョン管理する**: 一度顧客コードに使われると、コード変更を安易に頼めない。更新の唯一の手段は新バージョンのリリース。HTTP ヘッダー等でバージョンを識別し、標準的なロードバランサーが適切なバージョンへ振り分けられる設計にする。

## レビュー観点

- [ ] 想定利用者(開発者)とそのワークフローが明確か
- [ ] 実世界のメンタルモデルに沿った名前と流れか
- [ ] 「最初の呼び出し」までの手数・ボイラープレートが最小か
- [ ] 結果をそのまま次の呼び出しへ渡せるか
- [ ] 1 エンドポイント/メソッド 1 責務か。不確かな機能が混ざっていないか
- [ ] 標準(認証・認可など)を使っているか
- [ ] バージョニング方式が初日から決まっているか
- [ ] 公開範囲は必要最小限か。情報漏洩しうるデータは含まれないか
- [ ] 公開前に内部で使って検証したか
